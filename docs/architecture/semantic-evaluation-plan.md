# Career-Ops v1.2 — Semantic Evaluation Plan & Benchmark Methodology

**Architecture Milestone:** v1.2 — Semantic Intelligence Audit & System-1 Refactor Specification  
**Status:** DRAFT SPECIFICATION (AUDIT-ONLY — NO BENCHMARK FABRICATION)  
**Primary Focus:** Israeli Early-Career Software Engineering & Applied AI Hiring Ecosystem  

---

## 1. Objective & Evaluation Principles

Before any heuristic or regex is migrated to System 1 in production, its semantic behavior must be quantitatively validated against an independently annotated, human-adjudicated ground truth benchmark.

### Core Evaluation Invariants:
1. **NO MODEL-AS-GROUND-TRUTH:**
   Benchmark ground truth labels must NEVER be generated by an LLM and declared ground truth. Every gold label in the benchmark corpus must be reviewed and confirmed by human engineers.
2. **ASYMMETRIC LOSS FUNCTION (FALSE REJECT PENALTY):**
   In early-career job search pipelines, a **False Reject** (discarding a genuine, high-quality junior or entry-level job the candidate was qualified for) has a far higher cost than a **False Positive** (passing a borderline role to human review). The evaluation metric weights False Rejects 5x higher than False Positives.
3. **FAIL-SAFE ABSTENTION ACCOUNTING:**
   When a model reports `UNCERTAIN` or escalates to `NEEDS_REVIEW`, this is accounted for explicitly as **Abstention**. Abstentions do not count as correct extractions, but neither do they cause silent failure. Abstention coverage is tracked as a first-class operational metric.
4. **DATA PRIVACY & REPRODUCIBILITY:**
   All job descriptions in the benchmark must originate from public postings with licensing compliance. Candidate profiles used in matching tests must be synthetic archetypes or explicitly consented user profiles. Personal PII is strictly excluded.

## 2. Benchmark Corpus Methodology & Sampling Strategy

The benchmark requires a representative corpus of **300 real job postings** curated specifically across Israeli and global remote hiring channels.

### Target Cohort Composition (300 Postings):

| Segment | Target Count | Language | Primary Sourcing Channels | Target Characteristics |
|---|---|---|---|---|
| **Early-Career AI / ML** | 75 | EN / HE | Geektime Insider, Comeet, LinkedIn, Ashby | Junior AI Engineer, ML Associate, Data Science Grad, LLM Intern |
| **Early-Career Software / Backend** | 75 | EN / HE | Greenhouse, Lever, Workday, TechAviv | Junior Backend (Python/Go/Node), Full Stack, Cloud Systems |
| **Mid / Senior Boundary Roles** | 50 | EN | Greenhouse, Ashby, Lever | Roles asking 2-4 YOE or ambiguous titles ("Member of Tech Staff", "AI Specialist") |
| **Strict Legal / Cleared Roles** | 30 | HE / EN | Israeli Defense Tech (Elbit, Rafael, IAI), Gov | Explicit security clearance, Israeli citizenship, strict BSc requirements |
| **Aggregator & Ghost Postings** | 40 | EN / HE | Job aggregators (LinkedIn reposts, Indeed, Glassdoor) | Stale roles, re-posted 3+ times, agency intermediary, missing employer |
| **Adversarial & Edge Cases** | 30 | EN / HE | Real edge-case postings | Postings with prompt injection tokens, inverted titles, foreign degrees, Roman numerals |

### Splitting Methodology:
- **Chronological / Company Cluster Split:** To prevent data leakage, postings from the same company or identical requisition family are assigned exclusively to either Train (40%), Validation (30%), or Test Holdout (30%). Never split the same company across train and holdout.

## 3. Benchmark Schema & Gold Annotation Guidelines

Each benchmark sample is formatted as a structured JSON record:

```typescript
export interface BenchmarkSample {
  sample_id: string;               // e.g. "CORPUS-IL-2026-0042"
  metadata: {
    source_url: string;
    company: string;
    raw_title: string;
    sourcing_date: string;
    language: "en" | "he" | "mixed";
    jurisdiction: "IL" | "GLOBAL_REMOTE" | "US" | "EU";
  };
  raw_jd_text: string;
  gold_annotations: {
    role_family: string;           // Canonical role family
    seniority_level: "INTERN" | "JUNIOR" | "ENTRY" | "MID" | "SENIOR" | "STAFF_PRINCIPAL";
    is_early_career_friendly: boolean;
    required_yoe: number | null;
    preferred_yoe: number | null;
    yoe_is_ambiguous: boolean;
    required_skills: Array<{ name: string; category: string; verbatim_span: string }>;
    preferred_skills: Array<{ name: string; category: string; verbatim_span: string }>;
    degree_requirement: {
      min_level: "NONE" | "ASSOCIATE" | "BACHELOR" | "MASTER" | "DOCTORATE";
      fields: string[];
      equivalent_experience_allowed: boolean;
    };
    work_model: "REMOTE" | "HYBRID" | "ONSITE";
    legal_requirements: {
      work_authorization_required: boolean;
      security_clearance_required: boolean;
      citizenship_required: boolean;
    };
    duplicate_cluster_id?: string; // Identifier shared by duplicates
    status: "UNLABELED" | "MODEL_PROPOSED" | "HUMAN_REVIEWED" | "DUAL_HUMAN_VERIFIED" | "ADJUDICATED";
    annotator_id?: string; // Reviewer or model signature
    annotation_date: string;
  };
}
```

### Human Annotation Protocol:
See detailed operational guidelines in `docs/architecture/annotation-protocol.md` and CLI tools in `scripts/annotate-benchmark.mjs`.
1. **Annotation States:** Explicitly distinguishes `MODEL_PROPOSED` / synthetic labels from `DUAL_HUMAN_VERIFIED` ground truth.
2. **Dual Independent Annotation:** Each production benchmark posting is annotated by two independent technical reviewers using an isolated labeling interface.
3. **Conflict Adjudication:** Disagreements in YOE, seniority, or requirement importance (>5% difference) are escalated to a senior engineer for final binding consensus (`ADJUDICATED`).
4. **Verbatim Span Rule:** Every technical skill and legal requirement must highlight an exact character span in the source text (`raw_jd_text.slice(start, end) === verbatim_quote`). No inferred skill is permitted without textual provenance.

## 4. Evaluation Metrics & Formulae

```
                                  EVALUATION MATRIX
  ┌──────────────────────┬────────────────────────┬────────────────────────────────────────┐
  │ Category             │ Metric                 │ Mathematical Formula                   │
  ├──────────────────────┼────────────────────────┼────────────────────────────────────────┤
  │ Extraction           │ Precision, Recall, F1  │ TP / (TP + FP), TP / (TP + FN)         │
  │ Skill Normalization  │ Concept Accuracy       │ Correct Canonical Matches / Total Extr │
  │ Fit Decision         │ False Reject Rate      │ Rejected Qualified / Total Qualified   │
  │ Fit Decision         │ False Apply Rate       │ Applied Unqualified / Total Unqual     │
  │ Deduplication        │ Dedup Precision/Recall │ True Dups Detected / Predicted Dups    │
  │ Calibration          │ Expected Calibr. Error │ sum( |acc(b) - conf(b)| * |b|/N )      │
  │ Operational          │ Latency & Calls / Job  │ p50, p95 elapsed ms; LLM calls/job     │
  └──────────────────────┴────────────────────────┴────────────────────────────────────────┘
```

### Detailed Metric Definitions:

#### 1. Extraction Metrics (YOE, Education, Work Model)
- **Precision:** $\frac{TP}{TP + FP}$ — Fraction of extracted requirements that match gold ground truth.
- **Recall:** $\frac{TP}{TP + FN}$ — Fraction of true requirements identified by the model.
- **Numeric YOE Tolerance:** An extraction is counted as True Positive if $|extracted - gold| \le 0.5$ years. A model that extracts preferred YOE as mandatory is counted as False Positive.

#### 2. Skill Normalization Metrics
- **Concept Match Accuracy:** Percentage of extracted surface forms mapped to the correct canonical `SkillConcept` ID.
- **False Skill Match Rate:** Frequency with which unrelated candidate skills are matched to a requirement (e.g. mapping "Java" to "JavaScript"). Must be $< 1.0\%$.
- **Missed Skill Rate:** Frequency with which a candidate possessing an equivalent skill is reported as having a gap (e.g. candidate has "FastAPI", JD asks for "Python Backend", marked as gap). Must be $< 3.0\%$.

#### 3. Candidate Fit & Policy Metrics
- **False Reject Rate (FRR):**
  $$\text{FRR} = \frac{\text{Jobs where Gold = Strong/Reasonable, but Model = Reject}}{\text{Total Gold Strong/Reasonable Jobs}}$$
  *Target:* $\text{FRR} < 2.0\%$. (Zero tolerance for silent false drops of junior roles).
- **False Positive Apply Rate (FPAR):**
  $$\text{FPAR} = \frac{\text{Jobs where Gold = Reject, but Model = Strong/Apply}}{\text{Total Gold Reject Jobs}}$$
  *Target:* $\text{FPAR} < 5.0\%$.

#### 4. Ranking Metrics (Shortlist Quality)
- **Precision@10:** Fraction of top 10 ranked jobs that are confirmed high fit.
- **NDCG@10:** Normalized Discounted Cumulative Gain assessing ranking order quality against gold human preference scores.

#### 5. Deduplication Metrics
- **Duplicate Precision:** Fraction of predicted duplicate pairs that are true duplicate requisitions.
- **Duplicate Recall:** Fraction of true duplicate requisitions identified.
- **Destructive Loss:** Number of distinct job opportunities erroneously merged into an existing row. Must be strictly **0**.

#### 6. Calibration Metric
- **Expected Calibration Error (ECE):**
  $$\text{ECE} = \sum_{m=1}^{M} \frac{|B_m|}{N} \left| \text{acc}(B_m) - \text{conf}(B_m) \right|$$
  Measures whether a reported confidence of 0.85 corresponds to an 85% empirical accuracy.

#### 7. Operational & Cost Metrics
- **Latency per Job (p50 / p95):** Elapsed milliseconds for full extraction and matching. Target: p50 $< 2500\text{ms}$.
- **Gateway Calls per Job:** Average number of LLM invocations per hydrated job. Target: $\le 1.2$ calls/job (achieved via task bundling).
- **System 2 Escalation Rate:** Percentage of jobs requiring System 2 deep reasoning. Target: $5\% - 10\%$.
- **Semantic Cache Hit Rate:** Target: $> 35\%$ across batch scanning.

## 5. Holdout Validation & Calibration Protocol

Before deploying any System-1 task to production:
1. **Zero-Touch Holdout:** The 30% holdout test partition is strictly sealed. No prompt engineering, model tuning, or heuristic adjustments may be made against holdout data.
2. **Confidence Calibration Sweep:** The confidence threshold for System-2 escalation (nominally 0.75) is calibrated on the Validation partition to achieve an ECE $< 0.05$ before freezing for holdout evaluation.
3. **Statistical Significance:** All metric comparisons between legacy heuristics and System 1 must report 95% bootstrap confidence intervals ($N=1000$ resamples).
4. **Hard Promotion Gate:** A task is approved for production shadow deployment only if holdout metrics exceed legacy heuristic baselines across both Precision and Recall with $p < 0.01$.
